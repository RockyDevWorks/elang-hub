# ELANG Rust SDK — Archive/Parser Boundary Security Review

**Repo:** `/opt/data/elang-rs` @ `4d90a16` (detached HEAD) · **Read-only investigation, 0 files modified**
**Scope:** H0501 threat-modeling input for ELANG Hub's validation service.

---

## 1. Decompression bomb protection

**Verdict: DEFENDED — by absolute byte ceilings, not by a compression-ratio cap.** There is **no ratio check anywhere** (`rg -i ratio` over `elang-container`/`elang-core`/`elang-reader` returns zero functional hits). The defense is a three-layer absolute cap, enforced _before_ allocation.

### 1.1 The container IS compressed (Zstandard)

`crates/elang-container/src/index.rs:67`:

```rust
pub const COMPRESSION_ZSTD: u8 = 1;
```

`crates/elang-container/src/index.rs:479-481` — a non-Zstd compression byte is rejected at index-decode time:

```rust
if compression != COMPRESSION_ZSTD {
    return Err(malformed("index entry compression code is not Zstd (1)"));
}
```

Each resource is one independent Zstd frame. `crates/elang-container/src/frame.rs:480` is the only decode entry point.

### 1.2 Layer A — frame header is inspected before any decompression`crates/elang-container/src/frame.rs:480-482`:

```rust
pub fn decode(bytes: &[u8], budget: &mut DecodeBudget) -> Result<Vec<u8>> {
    let header = inspect(bytes)?;
    let charged = budget.charged(header.content_size)?;
```

`inspect` performs **no decompression** (`frame.rs:154`: _"Performs *no* decompression, so it is safe to call on arbitrary bytes"_).

`frame.rs:228-233` — a frame **must declare its decompressed size**; the field is not optional:

```rust
if fcs_len == 0 {
    return Err(frame_err(
        "FRAME_MISSING_CONTENT_SIZE",
        "frame does not declare its decompressed size",
    ));
}
```

This is the key structural property: **the attacker cannot under-declare**, so a bomb's true size is known before a single byte is produced.

### 1.3 Layer B — window ceiling (128 MiB)

`crates/elang-container/src/frame.rs:307-312`:

```rust
if window_size > MAX_ZSTD_WINDOW_BYTES {
    return Err(frame_err(
        "FRAME_WINDOW_TOO_LARGE",
        format!("frame window {window_size} exceeds the {MAX_ZSTD_WINDOW_BYTES}-byte ceiling"),
    ));
}
```

`crates/elang-core/src/limits.rs:22`: `pub const MAX_ZSTD_WINDOW_BYTES: u64 = 128 * 1024 * 1024;`

Rationale documented at `frame.rs:52-56`: _"A larger window is not merely wasteful, it is a denial-of-service vector: libzstd allocates a history buffer proportional to the window before producing any output byte."_

### 1.4 Layer C — per-resource + aggregate decode budgets

`crates/elang-container/src/frame.rs:429-458` — `DecodeBudget::charged()`:

```rust
fn charged(&self, bytes: u64) -> Result<Self> {
    if bytes > self.max_resource_bytes {
        return Err(frame_err(
            "DECOMPRESSION_BUDGET_EXCEEDED",
            format!("resource declares {bytes} bytes, per-resource ceiling is {}",
                self.max_resource_bytes),
        ));
    }
    ...
    if total > self.max_aggregate_bytes {
        return Err(frame_err("DECOMPRESSION_BUDGET_EXCEEDED", ...));
    }
```

Critically, `charged()` is called at `frame.rs:482` **before** `DCtx::create()` at `frame.rs:484` — so the aggregate charge is debited from the _declared_ size before any allocation grows.

Decode is **streaming, not a full in-memory expand**. `frame.rs:463`: `const DECODE_SCRATCH: usize = 128 * 1024;` and `frame.rs:491-546` is a streaming loop with a live re-check at `frame.rs:525-533`:

```rust
if total > charged.max_resource_bytes {
    return Err(frame_err("DECOMPRESSION_BUDGET_EXCEEDED", ...));
}
```

`frame.rs:560` commits the aggregate only after bytes exist: `budget.aggregate_used = charged.aggregate_used;` — a failed decode cannot leak budget.

### 1.5 Layer D — ceilings in `elang-core::limits.rs`

| Constant                           | Value  | Line           |
| ---------------------------------- | ------ | -------------- |
| `MAX_GENERIC_RESOURCE_BYTES`       | 1 GiB  | `limits.rs:35` |
| `MAX_EPF_BYTES`                    | 1 MiB  | `limits.rs:29` |
| `MAX_INTEGRITY_BYTES`              | 16 MiB | `limits.rs:31` |

Standalone probe crate in scratch, compiled against the repo's `elang-container` (no repo files touched; probe since deleted):

**What this means for the Hub:** a 42-byte-zip-equivalent is _not_ the threat model here. The real bound is **1 GiB per resource / 8 GiB aggregate**, and a ~2 KB frame genuinely expands to 64 MiB and is accepted. The SDK's ceiling is a _memory_ ceiling, not a _ratio_ ceiling. See §5 for the ratio caveat.

### 1.7 One real gap in the bomb story: no total-archive-size ceiling on the read path

`MAX_COMPRESSED_ARCHIVE_BYTES` (6 GiB, `limits.rs:10`) is **writer-side only**. `rg 'MAX_COMPRESSED_ARCHIVE_BYTES' crates/elang-container crates/elang-reader crates/elang-cli` → **zero hits**. This is explicitly documented as a known gap in `docs/security-limits.md:47`:

> _"**Writer-side only.** ... **The reader does not enforce it** — the reader bounds expansion through `MAX_UNCOMPRESSED_AGGREGATE_BYTES` and the per-resource ceilings instead. Reader-side enforcement and the recommended-size warning are tracked as open task **T0420** ... status *Partial*."_

Consequence: `Package::open` (`crates/elang-reader/src/package.rs:72-98`) and the CLI's `read_archive_file` (`crates/elang-cli/src/main.rs:414`, plain `fs::read`) will accept an arbitrarily large `.elang` file and copy it into memory (`package.rs:94`: `archive: archive.to_vec()`). **The Hub must enforce the upload byte ceiling itself, before invoking the SDK.**

## 2. Path traversal protection in archive entry names

**Verdict: DEFENDED at the parse layer, and the SDK never writes to disk — path traversal is a non-issue for a Hub that only calls inspect/verify/validate.**

### 2.1 Lexical validation of every index path

`crates/elang-core/src/ids.rs:24-75` — `ResourcePath::new` is the sole constructor:

```rust
if s.starts_with('/') {                                    // :40  absolute
    return Err(err(Category::ResourcePath, "PATH_ABSOLUTE", "absolute path"));
}
if looks_drive_absolute(&s) {                              // :48  C:\foo
    return Err(err(Category::ResourcePath, "PATH_ABSOLUTE", "drive-absolute path"));
}
if s.contains('\\') {                                      // :55  backslash
    return Err(err(Category::ResourcePath, "PATH_BACKSLASH", "backslash in path"));
}
if s.contains('\0') {                                      // :62  NUL
    return Err(err(Category::ResourcePath, "PATH_NUL", "NUL in path"));
}
for segment in s.split('/') {                              // :65-73  . / .. / empty
    if segment.is_empty() || segment == "." || segment == ".." {
        return Err(err(Category::ResourcePath, "PATH_EMPTY_SEGMENT",
            "empty, '.' or '..' path segment"));
    }
}
```

Plus `PATH_TOO_LONG` at `ids.rs:33-39` (≤1024 UTF-8 bytes, `limits.rs:40`).

`looks_drive_absolute` at `ids.rs:90-92`:

```rust
fn looks_drive_absolute(s: &str) -> bool {
    matches!(s.as_bytes(), [drive, b':', ..] if drive.is_ascii_alphabetic())
}
```

**No symlink entries exist in the format** — the index entry carries only path/offset/sizes/digest/compression-byte (`crates/elang-container/src/index.rs:483-492`). There is no file-mode or link-target field, so a symlink entry cannot be expressed.

### 2.2 The validation is on the _decode_ path, not merely on write

`crates/elang-container/src/index.rs:452-465` — every path read out of untrusted index bytes goes through UTF-8 → NFC → `ResourcePath::new`:

```rust
let path_str = std::str::from_utf8(path_slice)
    .map_err(|_| path_err("PATH_NOT_UTF8", "resource path is not valid UTF-8"))?;
if !elang_unicode::is_nfc(path_str) {
    return Err(path_err("PATH_NOT_NFC", "resource path is not in Unicode NFC"));
}
let path = elang_core::ResourcePath::new(path_str)?;
```

### 2.3 The SDK never touches the filesystem

`rg 'std::fs::|File::create|fs::write|OpenOptions' crates/elang-{container,reader,core,kdl,epf,eld,integrity}/src` → **only `#[cfg(test)]` fixture reads** (`container/src/footer.rs:288`, `header.rs:389`, `index.rs:562`, `testdata.rs:32-50`). No production write path exists.

**Precise answer for the Hub:** the library API (`Package::open/inspect/verify/validate`) does **not** extract to disk. Path traversal is therefore **not a filesystem risk for a Hub that calls the SDK's read APIs**. It becomes one only if the Hub shells out to `elang unpack`.

### 2.4 `elang unpack` (CLI only) has defence in depth

- `crates/elang-cli/src/main.rs:672-676` — refuses to write through an existing symlink:

```rust
 Ok(meta) if meta.file_type().is_symlink() => {
     diag!("refusing to write through symlink: {}", target.display());
     return 1;
```

- `main.rs:689-693` — `OpenOptions::new().write(true).create_new(true)` (`O_CREAT|O_EXCL`), so an existing file is never silently clobbered.
- `main.rs:572-606` — `create_safe_parent()` walks parent components, and for any symlink resolves it and requires it to stay under `base`:
  ```rust
  if !canon.starts_with(base) {
      return Err(format!("symlink escapes the output directory: {}", current.display()));
  }
  ```
- `main.rs:677-688` — refuses to overwrite an existing file without `--force`.

**Caveat, stated by the project itself** (`docs/security-limits.md:116`): _"The code does **not** use `O_NOFOLLOW`; see the TOCTOU note."_ The `symlink_metadata`-then-`create_new` sequence is a check-then-use race. Irrelevant to the Hub unless it unpacks.

## 3. Resource-count / size limits

**Verdict: DEFENDED, with ceilings enforced at every layer.**

### 3.1 Resource count — 25,000

`crates/elang-core/src/limits.rs:16`: `pub const MAX_RESOURCES: u32 = 25_000;`

Enforced **twice**, at both the byte-count and iteration levels:

- `crates/elang-container/src/index.rs:289-295` — before the entry loop:
  ```rust
  let count = read_u32(bytes, 12);
  if count > elang_core::limits::MAX_RESOURCES {
      return Err(index_err("INDEX_COUNT_OUT_OF_RANGE",
          "index declares more resources than the archive ceiling"));
  }
  ```
- `crates/elang-core/src/index.rs:164-170` — `ResourceIndex::new`:
  ```rust
  if entries.len() > MAX_RESOURCES as usize {
      return Err(limit_err("LIMIT_RESOURCES_ARCHIVE", ...));
  ```

Critically, the check at `index.rs:289` precedes `Vec::with_capacity(count)` at `index.rs:298`, so a hostile `count = 4 billion` does not pre-allocate.

### 3.2 Index size — 32 MiB, enforced before iteration

`limits.rs:18`: `pub const MAX_INDEX_BYTES: u64 = 32 * 1024 * 1024;`
`crates/elang-container/src/index.rs:268-275`:

```rust
if bytes.len() > max_index_bytes {
    return Err(index_err("INDEX_SIZE_OUT_OF_RANGE", "index exceeds the 32 MiB ceiling"));
}
```

Comment at `index.rs:264-267` states the intent: _"so a maliciously large index cannot pin the parser in an O(bytes) walk."_
Also enforced at `crates/elang-container/src/footer.rs:132-136` (footer-declared index size must be in `MIN_INDEX_SIZE..=MAX_INDEX_SIZE`) and `crates/elang-container/src/footer.rs:204-213` (framing: `index_offset + index_size + 64 == file_size`).

### 3.3 Per-resource and aggregate uncompressed sizes

- Per-resource: `crates/elang-core/src/index.rs:72-77` (`INDEX_SIZE_OVER_CEILING`) and `crates/elang-container/src/layout.rs:319-324`.
- Aggregate: `crates/elang-core/src/index.rs:187-198` and `crates/elang-container/src/layout.rs:325-334`:
  ```rust
  total_uncompressed = total_uncompressed
      .checked_add(entry.uncompressed_size())
      .filter(|total| *total <= MAX_UNCOMPRESSED_AGGREGATE_BYTES)
      .ok_or_else(|| Error::new("LIMIT_UNCOMPRESSED_AGGREGATE", Category::Limit, ...))?;
  ```
  The `.filter()` sits on the `checked_add` result, so the ceiling test and the overflow test are the same expression — no wrap path.

### 3.4 Frame layout — contiguity, no gaps/overlaps/unindexed bytes

`crates/elang-container/src/layout.rs:120-207` (`validate_layout`) rejects `FRAME_LAYOUT_GAP`, `FRAME_LAYOUT_OVERLAP`, `FRAME_LAYOUT_UNINDEXED_BYTES`, `FRAME_LAYOUT_TRAILING_BYTES`, and zero-length frames (`layout.rs:178-183`).

### 3.5 Per-resource class-specific ceilings are enforced at decode

`crates/elang-reader/src/stages.rs:60` (integrity, 16 MiB), `:106` (EPF, 1 MiB), `:174` (ELD, 1 GiB), `:132-133` (stage 11:1 GiB per-resource, 8 GiB aggregate). Each routes through `decode_indexed_resource` → `DecodeBudget::new(max_resource)` (`stages.rs:215-216`).

## 4. Parser-level abuse limits

**Verdict: DEFENDED for KDL/ELD. Two gaps noted (4.3, 4.4).**

### 4.1 KDL recursion depth

`crates/elang-kdl/src/parse.rs:251-256`:

```rust
fn parse_node(&mut self, depth: usize) -> Result<KdlNode, ParseError> {
    if depth >= elang_core::limits::MAX_KDL_NESTING_DEPTH {
        return Err(self.error_here(ErrorCode::NestingTooDeep,
```

`limits.rs:45`: `pub const MAX_KDL_NESTING_DEPTH: usize = 64;` — checked _before_ the recursive descent, so it is a genuine guard, not a post-hoc check.

### 4.2 ELD condition nesting depth (separate, tighter budget)

`crates/elang-eld/src/when.rs:54`: `pub const MAX_NESTING_DEPTH: usize = 8;`
`crates/elang-eld/src/when.rs:427-438`:

```rust
if depth > MAX_NESTING_DEPTH
    && !matches!(name, "word-position" | "syllable-position" | "previous-phoneme" | "next-phoneme")

    return Err(when_err_at(node.span(), "WHEN_TOO_DEEP", ...));
```

### 4.3 JSON / TOML — NOT FOUND as an attack surface

**No JSON or TOML parser in the SDK consumes untrusted input.** The only `serde_json` usage is `crates/elang-repertoire/src/repertoire.rs:190` and `:327`, parsing `REPERTOIRE_JSON` — which is `include_str!`-embedded at compile time (`repertoire.rs:30`: `pub const REPERTOIRE_JSON: &str = include_str!("../../../specs/schema/ipa-v1.json");`). It is not attacker-controlled. `rg 'toml'` over the production crates → **zero hits**. So "recursion-depth guard for nested JSON/TOML" is **NOT APPLICABLE** to the archive path; KDL is the archive's document format and it has the depth guard above.

### 4.4 Two real gaps in the parser-abuse story

**(a) Archive-wide KDL budgets never accumulate in the reader.** `MAX_NODES_PER_ARCHIVE` (10M, `limits.rs:59`) and `MAX_DECODED_STRING_BYTES_PER_ARCHIVE` (1 GiB, `limits.rs:67`) exist and the KDL crate supports them — `crates/elang-kdl/src/budget.rs:88-108` initialises both, and `budget.rs:118-124` documents that _"The container layer drives this across sequential resources by calling `parse_with_budgets` with the same tracker."_ **The reader does not do this.** `crates/elang-reader/src/stages.rs:35` imports `use elang_kdl::parse as kdl_parse;` — the convenience wrapper — and `crates/elang-kdl/src/parse.rs:52-55` creates a **fresh** `BudgetTracker::new()` per call:

```rust
pub fn parse(input: &[u8]) -> Result<KdlDocument, ParseError> {
    let mut budgets = BudgetTracker::new();
    parse_with_budgets(input, &mut budgets)
}
```

Same for `elang_epf::parse` (`crates/elang-epf/src/parse.rs:59-60`) and `elang_eld::parse` (`crates/elang-eld/src/parse.rs:51` → `elang_kdl::parse(input)`). `rg 'BudgetTracker' crates/elang-reader/src/` → **zero hits**.

_Practical impact:_ bounded by the 8 GiB aggregate byte ceiling and 25,000-resource count, so not unbounded — but the documented archive-wide node budget is effectively per-resource in practice. The 8 GiB byte ceiling is the real backstop. **This is a documentation-vs-implementation divergence, not an unbounded-memory hole.**

**(b) `MAX_RETAINED_DIAGNOSTICS` (100) is defined but unused in production.** `crates/elang-core/src/limits.rs:76`; the collector is implemented at `crates/elang-core/src/error.rs:199-204`:

```rust
pub fn push(&mut self, diagnostic: Diagnostic) {
    self.total = self.total.saturating_add(1);
    if self.retained.len() < MAX_RETAINED_DIAGNOSTICS {
        self.retained.push(diagnostic);
    }
}
```

But `rg 'Diagnostics' crates/` outside `elang-core/src/error.rs` → only re-exports and doc comments. The reader/CLI fail fast on the **first** error (`stages.rs:124`: _"Returns the first `INTEGRITY_HASH_MISMATCH`..."_; CLI `main.rs:507-512` returns on the first `Err`). **Diagnostic flooding is therefore not a concern — the opposite design.** `docs/security-limits.md:155-157` also flags `MAX_SEMANTIC_REFERENCES` and `MAX_SEMANTIC_TRAVERSAL_DEPTH` as _"reserved for ELD's semantic phase"_ and not yet enforced; `rg` confirms zero call sites outside `limits.rs` and the conformance manifest.

## 5. Is the container compressed? (and the ratio caveat)

**YES — resources are Zstandard-compressed, one frame per resource.**

- `crates/elang-container/src/index.rs:67`: `pub const COMPRESSION_ZSTD: u8 = 1;`
- Enforced at `index.rs:479-481`.
- `crates/elang-container/src/frame.rs` is the entire compression layer: hand-parsed header + `zstd-safe` streaming decode + `zstd-safe` canonical encode.
- Workspace pins `zstd = "=0.14.3"`, `zstd-safe = "=8.2.0"`, `zstd-sys = "=2.1.2"` (`Cargo.toml`), libzstd 1.5.7 (`frame.rs:70`: `PINNED_LIBZSTD_VERSION: u32 = 10_507`).

**The actual size-limit enforcement point is therefore NOT a raw-byte check but the `DecodeBudget` pair** (`crates/elang-container/src/frame.rs:388-397`):

```rust
pub struct DecodeBudget {
    pub max_resource_bytes: u64,      // 1 GiB for a generic resource
    pub max_aggregate_bytes: u64,     // 8 GiB across the archive
    pub aggregate_used: u64,
}
```

charged at `frame.rs:482`, re-checked mid-stream at `frame.rs:525-533`.

**Ratio caveat (important for the Hub's threat model):** the SDK enforces _absolute byte ceilings_, not a _ratio_. Empirically I measured **~32,700:1** expansion ratios being accepted (2,071 B → 64 MiB; 32,791 B → 1 GiB). A hostile `.elang` of a few hundred KB can therefore force the SDK to materialise 8 GiB. The bound is memory, not input size.

Also note `crates/elang-container/src/frame.rs:304-306`:

```rust
if single_segment {
    window_size = content_size;
}
```

For a single-segment frame the window _is_ the content size, so a single-segment frame over 128 MiB trips `FRAME_WINDOW_TOO_LARGE` instead. A **multi-segment** frame (descriptor `0x84` in my probe) keeps `window = 128 MiB` while `content_size` reaches 1 GiB — that is the shape that gets accepted at the ceiling.

**Gaps:** no fuzz target exercises the **full `Package::open`→`validate` pipeline** on a mutated whole-archive input, nor the **CLI binary**. The targets operate on component level (header/footer/index, single frame, single document). The `fuzz/corpus/` directory holds committed seeds; `fuzz/artifacts/<target>/campaign.log` records 60-second campaigns (e.g. `container_structure`: 1,612,290 runs, cov 512, peak RSS 261 MB — no crashes). CI matrix with per-target `max_len` and budgets: `.github/workflows/fuzz.yml:51-85`.

## 8. Can the SDK be run with bounded time / memory?

**Verdict: NO — the SDK exposes no resource-limit knobs. Bounds are compile-time constants; bounding must happen outside the process.**

- **No CLI flags.** `rg 'max-|--limit|--timeout|--max' crates/elang-cli/src/main.rs` → **zero hits**. Usage strings are minimal: `crates/elang-cli/src/main.rs:121-125`:
  ```rust
  const INSPECT_USAGE: &str = "usage: elang inspect <archive>\n";
  const VERIFY_USAGE: &str = "usage: elang verify <archive>\n";
  const VALIDATE_USAGE: &str = "usage: elang validate <archive>\n";
  ```
- **No budget-injection API on the reader.** `Package::open/verify/validate` take no budget parameter (`package.rs:72,129, 166`). The `DecodeBudget` ceilings are hardcoded at the call sites: `stages.rs:132-133` and `stages.rs:215`. `DecodeBudget::new()` is public (`frame.rs:403`) but the reader never accepts an injected one.
- **No sandboxing, no rate limiting, no concurrency model.** `docs/security-limits.md:196-204`:
  > _"The reader runs in the caller's process with the caller's permissions. ... The reader does not `seccomp`, does not drop capabilities, does not chroot."_
- **Single-threaded.** `docs/security-limits.md:215-221`.
- **Wall clock.** `docs/security-limits.md:339-347`: worst case 6 GiB compressed → 8 GiB uncompressed ≈ 16 s on one core. No cancellation/deadline facility in the SDK.
- **Memory.** `docs/security-limits.md:330-337`: provision ≥ archive-ceiling + 512 MiB RSS per concurrent reader. `Package::open` doubles the archive in memory (`fs::read` result + `archive.to_vec()` at `package.rs:94`).

**Implication for the Hub:** bound the process externally — `RLIMIT_AS` / cgroup memory limit, a wall-clock timeout (SIGKILL, not cooperative cancellation), and an upload-size ceiling enforced _before_ the CLI is invoked.

## Confidence and gaps

**High confidence (direct code + empirical execution):** the Zstandard compression model; the three-layer bomb defense and its exact ceilings; path-traversal validation (absolute, drive-absolute, backslash, NUL, `.`/`..`/empty, length); that the SDK never writes to disk; resource-count / index-size / per-resource / aggregate ceilings; KDL and ELD depth guards; the fuzz-target inventory; the public API surface; the absence of limit flags.

**Empirically validated** (real frames built and run against the repo's own `elang-container`, since deleted): 32,404:1 and 32,753:1 expansion ratios; the exact 1 GiB per-resource cutoff; the aggregate-cutoff error text; forged-header rejection.

**Could not verify / gaps:**

1. **`MAX_COMPRESSED_ARCHIVE_BYTES` read-path enforcement — confirmed ABSENT**, not merely unlocated. `docs/security-limits.md:47` corroborates; tracked as open task **T0420** / `REQ-FRAME-012`, status _Partial_ in `docs/traceability.md`. This is the highest-value finding for H0501.
2. **Archive-wide KDL budgets not threaded in the reader** (§4.4a). Verified by `rg 'BudgetTracker' crates/elang-reader/src/` → zero hits, and by reading the convenience wrappers. I did **not** construct an end-to-end archive that demonstrates a node-count overrun across many resources — the byte-level8 GiB ceiling is the effective backstop, so the practical exposure is bounded, but the _documented_ archive-wide node budget is not the operative limit.
3. **`MAX_SEMANTIC_REFERENCES` / `MAX_SEMANTIC_TRAVERSAL_DEPTH` are declared but unenforced** — `docs/security-limits.md:155-156` labels them _"reserved"_; `rg` finds no call sites outside `limits.rs` and the conformance manifest. The ELD depth guard that _is_ enforced is the separate `elang_eld::when::MAX_NESTING_DEPTH = 8`.
4. **`MAX_RETAINED_DIAGNOSTICS` is unused in production** (§4.4b) — harmless, since the reader fails fast on the first error, but the constant implies a collector that no production path exercises.
5. **No end-to-end archive-level fuzz target.** All fuzzing is component-level. A mutated-whole-`Package::open`→`validate` target does not exist.
6. **I did not measure real peak RSS** for an accepted 1 GiB / 8 GiB archive; `docs/peak-memory.md:73` states the literal ceiling cases were not run because they need the RAM to be valid on the host. My figures are from `VmHWM` in that doc plus my own frame-level probes.
7. **The TOCTOU in `elang unpack`** (`symlink_metadata` then `create_new`, no `O_NOFOLLOW`) is a race I did not attempt to exploit; the project documents it at `docs/security-limits.md:116`. Only relevant if the Hub invokes `unpack`.
8. **`Package::open` copies the entire archive** (`package.rs:94`) — for the CLI this means2× the archive resident before any decoding. I did not benchmark this.
